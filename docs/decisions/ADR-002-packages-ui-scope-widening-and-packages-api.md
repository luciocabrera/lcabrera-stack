# ADR-002: Widen `packages/ui` scope to whole compositions; add `packages/api`

**Status:** Accepted

## Context

After ADR-001's extraction, a second pass identified more reusable surface that the first pass's "Table's dependency closure" framing had missed, because it was scoped to _components Table depends on_, not _everything in the app that isn't genuinely app-specific_:

- `DevStyleXInject` — a generic StyleX/Vite dev-mode CSS injection component, zero app coupling (takes one `cssHref` prop). Any app on this same build pipeline needs the identical helper.
- The **Settings route's presentational composition** (`Settings.component.tsx`, `SettingsOptionSection.component.tsx`, their types/constants/stylex/tests, and the `toDraft`/`toGlobalNavigationPreferencesUpdate` utils) — verified by reading `Settings.component.tsx` directly: it has **no loader, no action, no route-coupling at all** — it reads and writes global preferences entirely through `GlobalSettingsContext`'s own hooks (already shared per ADR-001). Only `routes/settings/root.ts` (a two-line re-export) and `settings.meta.ts`'s registration point are genuinely per-app route wiring.
- `utils/filters` (`createDistinctFilterOptions.util.ts`, `createStaticFilterOptions.util.ts`) — Table-column-filter-option builders, typed directly against `Table.types.ts`, reusable wherever Table is.
- `utils/api` (`api.util.ts`, `fetchAndValidate.util.ts`, `buildPaginatedQueryParams.util.ts`, `fakeDelay.util.ts`) plus its two dependencies `constants/api.constants.ts` and `types/api.types.ts` — a generic HTTP-client-building toolkit, distinct from the app-specific `services/{carSales,enterpriseOrders,wideAlltypes150}.api.ts` files that consume it (those stay put; they're genuinely business-specific).

This establishes a broader principle than ADR-001's "move what Table needs": **the actual dividing line in this codebase is route wiring (loaders/actions/meta registration) vs. everything else**. A component being _inside_ a `routes/` folder does not make it app-specific if it has no data-fetching coupling — `Settings.component.tsx` is proof of this.

## Decision

1. **`packages/ui` absorbs whole reusable compositions, not just leaf components.** The Settings feature moved in its entirety (component, sub-component, types, constants, stylex, test, meta, and its two draft-computation utils) to `packages/ui/src/components/Settings/`. `apps/react-router/src/routes/settings/root.ts` is now a two-line re-export from `@repo/ui/components/Settings/*` — the only thing that stays app-side is the route registration itself.
2. **`DevStyleXInject` and `utils/filters` move into `packages/ui`** for the same reason as ADR-001's components: generic, zero app-specific coupling, needed wherever Table/StyleX is used.
3. **New package `packages/api` (`@repo/api`)** for networking utilities that are generic across _any_ app calling this monorepo's API layer, but are not UI at all — `api.util.ts` (base URL resolution), `fetchAndValidate.util.ts`, `buildPaginatedQueryParams.util.ts`, `fakeDelay.util.ts`, plus `api.constants.ts`/`api.types.ts`. Kept **separate from `packages/ui`** deliberately: this package has no React/StyleX dependency at all (confirmed — only `vitest` as a dev dependency), and mixing pure networking code into a component-library package would blur what `packages/ui` is for. It follows the same no-build, `package.json`-declares-real-deps, tsconfig/vite-alias-plus-StyleX-alias pattern as `packages/ui` (StyleX alias omitted — `packages/api` has no `.stylex.ts` files).
4. Business-specific API services (`services/*.api.ts`) stay in `apps/react-router` and now import the generic layer from `@repo/api/api` instead of `@/utils/api` — the split between "generic HTTP toolkit" and "this app's specific queries" is now an actual package boundary, not just a folder convention.
5. Vitest's `include` in `apps/react-router/vite.config.ts` gets a third entry for `../../packages/api/src/**/*.test.*`, for the same reason ADR-001 added one for `packages/ui`.
6. **`routes/utils/{isPersistCookieAction,shouldRevalidatePersistCookieAction}.util.ts`** also moved into `packages/ui/src/routing/` (alongside the loader-state utils ADR-001 already put there) — confirmed generic by usage, not assumption: both are consumed identically by four different business routes' `root.ts` files (`car-sales`, `car-sales-infinite`, `wide-alltypes-150`, `enterprise-orders`), and depend on nothing but `react-router` itself and the already-shared `globalSettings.constants`. Same "does it depend on anything route-specific?" test as the rest of this ADR — living inside a `routes/utils/` folder didn't make them route-specific, using them across four unrelated routes already proved they weren't.
7. **`AppProviders`** (`packages/ui/src/components/AppProviders/`) — a new component, not a move, composing `ThemeProvider` → `GlobalSettingsProvider` → `NotificationProvider` in the fixed nesting order every consuming app needs, taking `defaultTheme`/`initialTheme`/`globalSettings` as props (the route's loader supplies these; this component owns composition/order only). `apps/react-router/src/root/Root.component.tsx` now uses it instead of inlining the three providers directly.
8. **`utils/security` (`cspNonce.util.ts`, `security.constants.ts`)** moved into `packages/ui/src/utils/security/` — a pure function reading a standardized header off any web-standard `Request`, with zero framework coupling; any SSR entrypoint (including a second app's planned custom Express server) needs the identical contract. This did not fit either `packages/ui`'s "React/StyleX" framing or `packages/api`'s "HTTP-client" framing cleanly, but `packages/ui` already holds several non-React infra utilities from ADR-001 (`utils/theme`, `utils/urlState`, `utils/logger`) for the same reason (part of a dependency closure, not literally UI) — kept there for consistency rather than creating a third package for one small utility.

With this, `apps/react-router/src/utils/` is now empty of code entirely (only a stray `ARCHITECTURE.md` remains), joining `constants/` and `types/` from ADR-002's original pass.

9. **`AppShell`** (`packages/ui/src/components/AppShell/`) — the app frame previously named `RootContent`, private to `Root.component.tsx`. Renamed on the move (an internal helper name isn't a fitting public component name) and given its own `ARCHITECTURE.md`/tests, since it's now a first-class exported component: themed background, `AppNavigation`, a routed `<Outlet />`, `NotificationCenter`. `apps/react-router`'s `Root.component.tsx` shrank to just wiring loader data (`theme`, `globalSettings`) into `AppProviders`, with `AppShell` as its child — no local component definition left at all. `Root.component.test.tsx` was rewritten to match: it now only verifies the loader-to-props wiring (mocking `AppProviders`/`AppShell` directly), while `AppShell`'s own behavior (theme toggle, outlet, notification center) has its own dedicated test colocated with the component.
10. **`AppDocument`** (`packages/ui/src/components/AppDocument/`) — the `<html>`/`<head>`/`<body>` shell previously inlined in `Root.layout.tsx`'s `Layout` export. Takes `rootData` (typed as a minimal local `AppDocumentRootData = { cspNonce?: string }`, not the app's full root-loader return type) and `stylexCssHref` as props — both stay props rather than being sourced inside the component, deliberately: `rootData` comes from `useRouteLoaderData<typeof rootLoader>('root')`, and `rootLoader`'s type is app-specific; `stylexCssHref` is a per-app Vite `?url` import of that app's own compiled StyleX stylesheet (`import stylexCssHref from '../stylex.css?url'`), a build artifact that only exists per-app — there's no single stylesheet this package could import on every consuming app's behalf. `Root.layout.tsx` now only does the loader call and the `?url` import, passing both through. Tested via `renderToStaticMarkup` rather than `@testing-library/react`'s `render()`, since the component's root is `<html>` (invalid to mount inside the container div `render()` appends to `document.body`); `Meta`/`Links`/`Scripts`/`ScrollRestoration` are mocked since they throw ("You must render this element inside a `<HydratedRouter>` element") outside a live router context, the same reason `<Outlet>` gets mocked elsewhere in this codebase's tests.
11. **`persist-cookie`'s `action`** moved to `packages/ui/src/routing/persistCookie.action.ts` (renamed from kebab-case to match this folder's existing camelCase convention — `isPersistCookieAction.util.ts`, `shouldRevalidatePersistCookieAction.util.ts`). Confirmed generic: depends only on `react-router` and the already-shared `buildCookieString.util`, and the calling side (`usePersistCookieAction.hook.ts`, the `PERSIST_COOKIE_ACTION` path constant) was already fully inside `packages/ui` from earlier passes — this was the one remaining piece. `apps/react-router/src/routes/api/persist-cookie/root.ts` is now a single-line re-export, `route()` registration itself (in `routes.ts`) stays per-app since route registration is inherently app-specific wiring.
12. **`root.loader.ts`'s logic** extracted to `getRootLoaderData.util.ts` (`packages/ui/src/routing/`) — every dependency it used (`INITIAL_GLOBAL_SETTINGS`, `getGlobalSettingsFromCookie`, `getRequestCspNonce`, `getThemeFromCookie`) was already in `packages/ui`; the only app-specific piece was the `Route.LoaderArgs` type from that app's own React Router typegen (`../+types/root`). Since the root route has no dynamic params, typing the extracted function's argument as the plain web-standard `{ request: Request }` loses nothing and makes it usable from any app's root loader. `apps/react-router/src/root/root.loader.ts` is now a single-line re-export (`export { getRootLoaderData as loader } from '@repo/ui/routing/getRootLoaderData.util'`) — the app-specific `loader` name TypeScript infers for `useLoaderData`/`useRouteLoaderData` call sites is unaffected by re-exporting under a different name.
13. **`entry.server.tsx`/`entry.client.tsx`** — both are stock React Router framework-mode SSR/hydration boilerplate. `entry.client.tsx`'s hydration call (`hydrateApp.util.tsx`) is 100% generic with zero variation possible. `entry.server.tsx`'s `handleRequest` (`createHandleRequest.util.tsx`) has exactly one genuinely per-app value — `stylexCssHref`, each app's own compiled StyleX stylesheet URL — which stays a parameter; everything else (streaming render, bot/SPA-mode detection, abort-on-timeout, HEAD short-circuit, CSP nonce threading, preload header) moved as-is. React Router's own tooling expects `entry.server.tsx` to export a literal `streamTimeout` binding, so the factory returns `{ handleRequest, streamTimeout }` for the app file to re-export directly rather than trying to make `streamTimeout` itself importable from elsewhere. Confirmed worth doing, not just hypothetically: a second app's `entry.server.tsx` already existed as a **divergent, less-complete duplicate** of this exact file (missing CSP nonce handling, the preload header, and the `toError` normalization) — a concrete instance of the "have to write this in every app" problem already having happened once. Not touched here since that app was not consuming `packages/ui` yet — flagged to adopt `createHandleRequest`/`hydrateApp` rather than keep its own copy.

Verified beyond the standard gate for this change specifically, since it touches React Router's special-cased entry-point files: started the actual dev server and confirmed a real request round-trips end to end (200 response, correct `<html>` shell with `entry.client.tsx` module-preload and StyleX CSS link present), that the `/settings` route (itself moved in this ADR) renders correctly through the new `AppDocument`/`AppProviders`/`AppShell`/`Settings` chain together, and that a real `HEAD` request short-circuits with a 200 and no body — not just asserted via the unit test, but observed against a running server.

## Consequences

- Two shared packages now exist (`@repo/ui`, `@repo/api`), each with a clear one-sentence test for what belongs in it: does it render anything / depend on React or StyleX? If yes → `packages/ui`. If it's generic request/response plumbing with no UI concern → `packages/api`. Business-entity-specific API calls (car sales, enterprise orders) are neither — they stay app-local.
- `apps/react-router/src/constants/` and `apps/react-router/src/types/` are now empty of code (only stray `ARCHITECTURE.md` files remain, describing directories with nothing left in them) — worth a follow-up cleanup pass to either remove or rewrite those docs, not done here since it's cosmetic and out of scope for this pass.
- Any future component or util added to `apps/react-router` should be evaluated against the same test before it lands — reflexively defaulting to app-local and re-migrating later (as happened twice now) costs more than asking "does this actually depend on anything route-specific?" up front.
