# ADR-005: Generic `Form` component in `packages/ui`

**Status:** Accepted

## Context

A product spec called for a generic `Form` component in `packages/ui`, parallel to `Table`: the same "the component knows how to render itself from declarative config" philosophy (`columns` for `Table`, `fields` for `Form`), and `Form` must be exactly as agnostic to where its `fields` came from as `Table` already is about `columns` — whether hand-authored or computed server-side. This is built on the `useStore.hook.ts` primitive `Table` already established (ADR-001) — no new dependency.

Two decisions were corrected mid-implementation, before any code was written for them, based on direct user direction:

1. **`<Form>` (navigation), not `useFetcher().Form`, by default.** The original spec draft suggested `useFetcher()` uniformly, citing `usePersistCookieAction.hook.ts` as precedent. Checked against React Router's own `Form` vs. `useFetcher()` decision guide directly (not assumed): the documented criterion is whether the URL \_should* change. The first consumers — creating an entity, and starting a job that redirects to its detail page — are exactly the "significant context shift" case the guide names `<Form>` for, not the "stay on this list, don't navigate" case `useFetcher()` is for. `usePersistCookieAction`'s use of `useFetcher()` was correct for _that_ case (a background cookie write with no navigation) but was the wrong precedent for a generic create/edit/view form component. `Form` now defaults to RR7's native `<Form>` + `useNavigation()`; `useFetcher().Form` is kept as an explicit opt-in (`submission: 'fetcher'`) for a future non-navigating use case, not the default.
2. **`mode: 'create' | 'edit' | 'view'` is a first-class part of the contract**, not just create. In `view` mode every leaf field is forced disabled and the footer (submit/cancel) isn't rendered at all — the form is read-only, full stop. In `edit` mode the submit button is disabled and submission is blocked client-side unless at least one field's value actually differs from the pristine snapshot captured at mount — so an unmodified edit form never triggers a write. The first consuming routes only exercise `mode: 'create'`; `edit`/`view` have no real consumer yet, so they're covered by `Form.test.tsx`'s integration tests directly rather than by a real route.

## Decision

1. **Store pattern mirrors `Table` exactly** (per the `store-pattern` skill, which is MANDATORY reading before touching this kind of state) — **two stores in one `FormContext`**, not one combined store, matching `TableConfigContextValue`'s `columnsStore` + `metaStore` pairing rather than treating "one context" as "one store": `FormMetaState` (`mode` — low-frequency, form-level) and `FormFieldsState<TValues>` (`values`/`errors`/`initialValues` — high-frequency, every slice keyed by accessor), each behind its own thin `useSyncExternalStore` wrapper (`useMetaStore`/`useFieldsStore`, mirroring `Table`'s `useColumnsStore`/`useMetaStore`/`useFiltersStore`). Every selector hook (`useGetFieldValue`, `useGetFieldError`, `useGetFormMode`, `useGetIsFormDirty`) is a one-line call into the matching store-hook — including the accessor-keyed ones, the same shape as `Table`'s `useGetNormalizedColumn(columnKey)`/`FiltersData`'s `useGetFilterData(columnKey)`. The context itself lives behind a non-generic `createContext` erased at the provider boundary and restored via a generic cast on read (same technique as `TableDataContext`). Components only ever call selector hooks or action hooks (`useSetFieldValue`, `useSubmitForm`) — never `fieldsStore.get()`/`.set()` or `metaStore.get()`/`.set()` directly. `useSubmitForm` is the one action needing both stores (mode to gate the dirty check, values/initialValues to run it) — reading multiple stores from one action, snapshotting each once, is an explicitly allowed cross-store action responsibility (the same as `Table`'s `useSetColumnFilter` reading both `TableConfig` and `TableData`). `Form.component.tsx` composes `FormProvider` and delegates all actual rendering to a private `FormBody`, exactly as `Table.component.tsx` composes `TableDataProvider` and delegates to `TableContent`.

   **Correction, caught by architecture review, not by a test:** the first implementation used one combined `FormState` store with four selector hooks each independently reimplementing the full `useSyncExternalStore` triple, rather than factoring that boilerplate into shared `useFieldsStore`/`useMetaStore` hooks the way `Table` already does. It even had the exact keyed-selector precedent in hand (`FiltersData`'s `useGetFilterData(columnKey)` selecting `state[columnKey]` through a shared `useFiltersStore`) and didn't replicate it. Splitting `mode` out of the same store as `values` also isn't just stylistic: every `useSetFieldValue` write still wakes every subscriber of _whichever store it's in_ to re-run its selector (even when `useSyncExternalStore`'s snapshot-equality check prevents an actual re-render) — keeping high-frequency `values` out of the store that `mode` lives in means a keystroke doesn't invoke `mode`'s selector at all, the same reasoning `Table` already applies by keeping `columnsStore` separate from `dataStore`.

2. **Recursive field tree, one walker, reused three ways.** `FieldNode<TValues>` is a discriminated union: `group | row | tab | <leaf>`. `flattenFields.util.ts` is the single recursive walker; `getInitialValues`, `validateFields`, and the edit-mode dirty check all consume its flattened output rather than each re-implementing the recursion (the second draft of the _reference_ implementation this was studied against — `/home/lucio/workspaces/control-business-ui-ts/src/components/Form`, a different, unrelated project — had exactly this bug: `FormFields.tsx`/`getInitialData.ts`/`validateFields.ts` each independently reimplemented `group`/`row` recursion).
3. **Leaf types dispatch through a registry (`FormField.constants.ts`), not a switch.** `text | email | password | textarea | number | boolean | select | radio | date | datetime | custom`. Each concrete leaf component (`TextField`, `NumberField`, ...) is generic over its own `TValues`; the registry itself is typed as `Record<type, AnyFieldComponent>` with each entry cast at the registry boundary — the one intentional, narrowly-scoped `any`-adjacent cast in the whole component, confined to that single indirection point.
4. **Leaf renderers reuse the existing design system — verified by reading the real component prop types, not assumed:** `boolean` → `Checkbox` or `ToggleSwitch` (`variant` prop); `select` → `VirtualSelect` (static `options`, not the fetch-mode path `SelectFilterInput` uses); `radio` → `RadioOptionGroup`. `text`/`number`/`date` needed genuinely new bare inputs: checked `TextFilterInput`/`NumberFilterInput`/`DateFilterInput` first, confirmed they're tightly coupled to the filter-operator system (`operator`, `DataKey<TData>` props) and not extractable into a shared primitive without touching working Table filter code for uncertain benefit — so `TextField`/`NumberField`/`DateField` are new, but reuse the existing `filterBaseStyles` design tokens (`packages/ui/src/design-system/tokens/filters.stylex.ts`) and `NO_AUTOFILL_INPUT_PROPS` constant rather than inventing new input chrome.
5. **`VirtualSelect` has no native form control at all.** `SelectField` mirrors its current selection into hidden `<input type="hidden">` elements so RR7's `Form`/`fetcher.Form` still submits real `FormData` for it — everything else (native inputs, checkboxes, radios) participates automatically via `name`.
6. **`noValidate` on the `<form>` element**, discovered empirically via a failing test: leaf inputs still carry native `required`/`min`/`max` attributes for accessibility, but without `noValidate`, native HTML5 constraint validation intercepts the click _before_ the `submit` event — and therefore before `handleSubmit`/`preventDefault` — ever fires, silently defeating both the required-field client validation and the edit-mode dirty gate. RR7's own `Form` implementation calls the consumer's `onSubmit` first and checks `event.defaultPrevented` before doing its own submission — confirmed by reading its source directly — so `noValidate` plus our own JS gate is what makes that mechanism actually reachable.
7. **Client validation (`validateFields.util.ts`) is hand-rolled, not Zod**, per that spec's reasoning: it's progressive-enhancement-only instant feedback, and the consuming route's action + Zod schema remains the sole authority — duplicating Zod client-side would mean maintaining the same rules in two places for no gain, since the server can't be bypassed regardless.
8. **`serverErrors` (from a route's `useActionData()`) flows back into `fieldsStore`** via a `FormProvider` prop, re-synced with a `useEffect` keyed on the prop's identity — mirroring exactly how `TableDataProvider` re-syncs an incoming `dataState` prop into its own store on change. `mode` gets the same treatment for `metaStore`, in case a consumer re-renders `Form` with a different `mode` without a full remount.

## Consequences

- `packages/ui` gains `Form`, fully covered by `Form.test.tsx` (registry dispatch across every leaf type, group/row/tab nesting, required-field validation blocking submission, view-mode read-only enforcement, edit-mode dirty-gated submission) plus dedicated unit tests for `flattenFields`/`getInitialValues`/`validateFields`/`isFormDirty`. All exercised through `react-router`'s `createRoutesStub`, so the real RR7 `<Form>`/`useNavigation()`/action wiring is what's under test, not a mocked stand-in.
- Native checkboxes are omitted from `FormData` entirely when unchecked (standard HTML behavior) — any consuming action's Zod schema must treat an absent boolean field as `false`, not error on a missing key.
- `INVENTORY.md` updated with the new `Form` component entry.
- The first real consuming routes will only exercise `mode: 'create'` — `edit`/`view` remain proven only by this component's own tests until a route needs them.
