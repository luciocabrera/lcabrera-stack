# ADR-008: `packages/api` renamed to `packages/data-access`; Postgres pool/env utilities moved there from `packages/scan-ingestion`

**Status:** Superseded by [ADR-038](ADR-038-public-package-topology-by-runtime.md)

> The body below is left exactly as written — a dated record of what was true at
> the time, per its own Decision #1. `packages/data-access` has since been split
> by runtime into `@repo/api` (browser-safe) and `@repo/server` (Node-only), and
> the file names referenced here are now kebab-case. See ADR-038.

## Context

`packages/scan-ingestion`'s `getPool.util.ts`/`env.schema.ts` (ADR-007) were flagged for a reuse-placement review: this exact "read `DB_HOST/PORT/USER/PASSWORD/NAME` from env, construct a `pg.Pool`" pattern is duplicated — not just similarly, but with the identical `Pool` constructor shape and identical env var names — across `apps/api-server`, `apps/api-server-fast` (independently, one Zod-validated, one hand-rolled), and now `packages/scan-ingestion`. That's exactly the kind of reusable piece this monorepo's own convention says belongs in a shared `packages/*` workspace, not re-authored per consumer.

Two real constraints ruled out the two most obvious existing homes, confirmed by reading their actual code and documented charters, not assumed:

- **`packages/api`** (before this rename) has **zero** Node-only code or built-ins anywhere (`pg`, `fs`, `child_process`, etc.) — confirmed via grep. Its own `ARCHITECTURE.md` and `generate.ts`'s own comment both state it "runs in the browser (fetch utilities executed client-side)." Dropping a Node-only `pg.Pool` singleton there would have been a genuine architecture violation, not just an inconsistency.
- **`packages/utils`** is the closest structural fit (same subpath-`exports` convention this move uses), but its `ARCHITECTURE.md`/`README.md` explicitly mandate "pure, framework-agnostic, runtime-agnostic, no side effects." A stateful `Pool` singleton directly contradicts that documented charter as written.
- **`apps/shared`** (`api-shared`) already exists specifically to dedupe `apps/api-server`/`apps/api-server-fast`, and already holds Postgres-adjacent Node-only code (`dbSanity.repository.ts`) — the closest real precedent — but it lives under `apps/`, and `packages/scan-ingestion` depending on an app-level package would invert the normal dependency direction (packages depend on packages; apps depend on packages, not the reverse).

Decision, confirmed with the user: rename `packages/api` → `packages/data-access` and add a `db/` subtree there for the Postgres utilities, rather than inventing a fourth new package. `packages/ui` already established the exact precedent needed for one package legitimately mixing browser-context and Node-context code (`src/entry/`'s SSR utilities) — `packages/data-access` follows that same shape: `src/api/` (browser fetch, unchanged) alongside `src/db/` (Node-only Postgres), one `tsconfig.app.json` (`createAppTsConfig` + `types: ['node']` appended), no Node/browser project split needed since there's no `vite.config.ts`-anchored second project to anchor one around (same reasoning `packages/ui`'s own tsconfig entry already documents).

Explicitly **not** done now (confirmed with the user): `apps/api-server`/`apps/api-server-fast` are **not** refactored to adopt `@repo/data-access` in this pass — they're unrelated to the CQMS build; migrating their divergent Zod-vs-hand-rolled env parsing to the shared utility is a separate future task, now that the shared home exists for it.

## Decision

1. **`packages/api` → `packages/data-access`**, `@repo/api` → `@repo/data-access` everywhere: the package directory, `package.json`'s `name`, every `paths`/`resolve.alias` entry in `packages/ts-configs/generate.ts` (apps/react-router's app tsconfig, packages/ui's tsconfig, the renamed package's own tsconfig), `apps/react-router/vite.config.ts`'s `resolve.alias`, `apps/react-router/package.json`'s dependency, all three `apps/react-router/src/services/*.api.ts` import specifiers, and both `INVENTORY.md` files' prose references. Historical ADRs (ADR-002/003/004) that mention `packages/api` under its old name are left as-is — they're a dated record of what was true when written, not rewritten history; this ADR is the pointer for anyone reading them later.
2. **`getPool.util.ts`/`env.schema.ts` moved from `packages/scan-ingestion/src/db/` to `packages/data-access/src/db/`**, unchanged internally (same-directory relative import between the two stays valid in the new location). `packages/data-access/package.json` gains a **partial** `exports` map — `./db/env.schema` and `./db/getPool.util` only, not the pre-existing `src/api/*` files, which continue being consumed exclusively via tsconfig `paths`/Vite `resolve.alias` (bundler-only resolution that never consults `package.json` `exports` at all, confirmed empirically — adding a partial `exports` map doesn't affect them).
3. **Why the partial `exports` map matters, not just tidiness**: `packages/scan-ingestion` needs `@repo/data-access/db/*` to resolve in **two genuinely different runtimes** — Vite/Vitest/tsc (bundler-mode resolution, which already respects `package.json` `exports` for a _different_ workspace package, unlike the self-referencing-alias case ADR-007 hit) and, critically, **plain `node --experimental-strip-types`** (`db/runMigrations.ts`, `cli/ingest.cli.ts`) — where only genuine Node package resolution (a real `node_modules` symlink + a real `exports` map) works; tsconfig `paths` and Vite `resolve.alias` don't exist in that execution path at all (the same constraint ADR-007 already documented for scan-ingestion's _own_ self-reference, now applying one layer up, across a real package boundary). Verified by actually running the CLI wrapper end-to-end against a real temporary git repo and real Postgres rows — not just trusting `tsc`/`vitest`, per the same discipline ADR-007 established.
4. **`packages/scan-ingestion` gains `@repo/data-access: workspace:*`** as a real dependency (not just a type-only reference) — `ingestReport.ts`'s and `ingest.cli.ts`'s imports of `getPool`/`closePool`/`readEnvConfig` now cross a genuine package boundary via this specifier, no longer a same-package relative-vs-alias concern.
5. **`packages/data-access`'s own tsconfig mirrors `packages/ui`'s exact precedent** for a package mixing browser and Node contexts in one project — `createAppTsConfig` (not `createNodeTsConfig`) with `types: ['node']` appended, since `src/api/` still needs `vite/client`/DOM types (browser fetch, `Window`/`Location` in tests) and `src/db/` needs `node` types (`process.env`), and there's no `vite.config.ts`-anchored second project to split them into (same reasoning already written down for `packages/ui`'s tsconfig entry).

## Consequences

- The three-way duplication (`apps/api-server`, `apps/api-server-fast`, `packages/scan-ingestion` each independently reconstructing the same `Pool`/env pattern) now has one real shared home for the _pattern_ — `packages/data-access`'s `db/env.schema.ts`/`getPool.util.ts` — even though only `scan-ingestion` consumes it today. Migrating `apps/api-server`/`apps/api-server-fast` onto it is a deliberately deferred, separate task.
- `packages/data-access` is now genuinely two things in one package (browser fetch utilities + Node Postgres utilities), by design, matching `packages/ui`'s own already-accepted precedent for the same shape — not treated as an inconsistency to "fix" later.
- Full quality gate re-verified clean across every affected package after the rename: `packages/data-access` (8 tests, unchanged — no new tests added for the moved `db/` files yet), `packages/scan-ingestion` (30 tests, all passing unchanged, plus the CLI wrapper re-run end-to-end against a fresh temporary git repo and real Postgres rows), `packages/ui` (lint/typecheck clean, zero remaining `@repo/api` references), `apps/react-router` (lint/typecheck clean, 1 test passing, plus a real `vite dev` smoke test returning `200`).

## Verification performed

Repo-wide grep for `@repo/api`/`packages/api` before and after, confirming only historical ADRs (left untouched, by design) still contain the old name. `pnpm install` + `packages/ts-configs generate.ts` re-run. Per-package `vp fmt --check` / `vp lint` / `tsc --noEmit -p tsconfig.app.json` / `vp run test` across `packages/data-access`, `packages/scan-ingestion`, and `packages/ui` — all clean. `apps/react-router`: lint/typecheck clean, `vp run test` (1 test) passing, and a real `vite dev` server smoke test (`curl` → `200`). `packages/scan-ingestion`'s CLI wrapper (`node --experimental-strip-types src/cli/ingest.cli.ts --skill=... --run-dir=... --local-path=...`) re-run end-to-end against a fresh temporary git repository, confirming the cross-package `@repo/data-access/db/getPool.util` import resolves correctly under plain `node` execution (not just `tsc`/`vitest`), with the resulting Postgres rows queried directly before cleanup.
