# ADR-075 — The index does not list the ADRs

**Status:** Accepted

**Issue:** [#724](https://github.com/luciocabrera/vite-react-compiler/issues/724)

**Amends:** [ADR-048](./ADR-048-adr-taxonomy-and-one-sequence.md) — "Each home
carries a generated index". The index stays generated and stays gated; what it
generates no longer includes a row per ADR.

## Context

Each ADR home's `README.md` is generated by `vp run adr:verify -- --write` from
the directory beside it, and the gate fails when it is out of date. Until this
decision it rendered one table row per ADR, in number order.

An ADR always takes the highest free number, so its row always went at the end of
the table — the same insertion point for every branch. Git cannot merge two
insertions at one point, so **any two branches each adding an ADR conflicted on
that file**, whether or not their numbers collided.

## Problem

The conflict is cheap to resolve and expensive to have. A conflicting PR in this
repository skips every `pull_request` workflow; only SonarCloud reports. The
check record then freezes at whatever it was, showing a partial set of passing
checks with nothing failed and nothing pending — a state visually
indistinguishable from a green PR with fewer applicable checks.

On 2026-08-14 PR #719 (ADR-073) and PR #722 (ADR-074) both went `CONFLICTING`
when ADR-072 merged, with deliberately distinct numbers. #722 then hit it a
second time when #719 merged. Sequencing the numbers correctly is no defence,
because the numbers were never what collided.

## Decision

`renderIndex` takes a home and **no entries**. Each home's `README.md` carries
what is true of the home itself — its tier, its blurb, what happens to it at the
CQMS extraction, where the template is, and why it does not list the ADRs. Adding
an ADR therefore changes exactly one file, the ADR, so two ADR branches touch
disjoint paths and there is nothing left to conflict on.

The table it used to carry is produced on demand by `vp run adr:list`, which is
the [ADR-049](./ADR-049-findings-reports-are-produced-on-demand.md) split applied
to this file: what a tool derives from tracked state is produced when asked, not
committed.

Everything the gate did, it still does. `vp run adr:verify` fails on a stray ADR,
a malformed filename, an H1 whose number disagrees with its filename, a reused
number, a numbered draft, and an index that does not match what the generator
would write — including one edited by hand.

## Consequences

**What it costs.** Browsing `docs/decisions/` on GitHub no longer shows a list of
decision titles; it shows the directory, whose filenames carry the same titles in
kebab case, and a README that explains the home. Reading the titles as prose is
one command (`vp run adr:list`) rather than zero. ADR-048 argued for the table on
exactly this ground and it was a fair argument; it is outweighed by a conflict
that fires on every concurrent pair and takes the PR's check record with it.

**What it buys.** Two concurrent ADRs merge with no hand-resolution, so neither
PR loses its checks to a conflict on a file that nothing but a generator writes.

**The trap.** Giving `renderIndex` the directory back — however small the row —
restores the conflict in full. What catches that is a test on the **rendered
output**: it hands the function a directory by both routes a parameter could
arrive back through, and asserts no ADR is named in what comes out.

The shape of the function does not catch it, and believing otherwise is the
sharper trap. `Function.length` stops counting at the first defaulted parameter,
so `renderIndex = (home, entries = [])` with the rows restored reports arity 1,
renders nothing when called with one argument, and passes an arity check while
regenerating an index with a row per ADR. An earlier revision of this ADR claimed
the missing parameter was itself the guarantee; it was not.

## Alternatives considered

1. **`merge=union` on the three index files.** Cheap, no code, and rejected on
   evidence: it corrupts the file it is meant to protect. Oxfmt pads markdown
   table columns to the widest cell, so an ADR whose title is wider than every
   existing one re-pads the whole table — both sides then change every row, and
   union keeps both copies. A two-branch trial where one ADR had a long title
   merged with no conflict into an index holding twice as many rows as the
   directory has ADRs. Even with equal padding the driver is only half right:
   merging the second branch into `main` orders the rows correctly, but merging
   `main` into the second branch emits ours-then-theirs, which puts ADR-076 above
   ADR-075 and fails the gate. It would also have to be honoured by GitHub's own
   merge to fix the frozen check record at all, and a bare repository does not
   read a tree's `.gitattributes` without `--attr-source`.

2. **Regenerate the index in a merge or rebase hook.** Repairs the working tree
   after the fact, which is not where the cost is: GitHub has already marked the
   PR `CONFLICTING` and skipped its workflows by then. Hooks also do not run in a
   linked worktree the way this repo uses them.

3. **Regenerate the index on `main` in CI after each merge.** Branches would stop
   touching the file, but the branch-level gate would have to accept an index
   missing rows — which is exactly what a hand-deleted row looks like. That
   trades this fix for a hole in the guarantee the same issue insists on keeping.

4. **Keep the table and accept the conflict**, as the coordination task template
   already tells authors to. Rejected because the resolution was never the
   expensive part: two agents in one session read a frozen check record as
   current.
