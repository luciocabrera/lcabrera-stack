# ADR-006: CQMS Postgres schema provisioning

**Status:** Accepted

## Context

Implementation Plan step 3: provision the CQMS database schema from TECH_SPEC §2.3/§2.3a against the already-running local Postgres instance (`docker/local`), before `packages/scan-ingestion`'s TypeScript layer (step 4) is built on top of it.

Two things the user specified explicitly before any code was written:

1. **A new, dedicated database — not one of the existing ones.** `docker/local`'s shared Postgres instance already hosts `car_sales_db`, `nestjs`, and `personal_trainer` for unrelated apps; CQMS gets its own database, `cqms_db`.
2. **Not the default (`public`) schema — a properly named one.** Every CQMS object lives in a `cqms` schema, created explicitly and referenced with full `cqms.` qualification everywhere (tables, functions, procedure, views) — no reliance on session `search_path`, so every migration file and every future consumer query is self-contained and unambiguous regardless of how it's invoked.

## Decision

1. **`cqms_db` database, `cqms` schema, same shared Postgres container** — no new infra. Confirmed via `docker ps`/`docker-compose.yml` that `postgres_container` (Postgres 18.3) is the same instance every other app in this monorepo already uses, with a single shared superuser (`root`) and per-app database isolation (`car_sales_db`, `nestjs`, `personal_trainer`) — `cqms_db` follows that exact existing convention rather than inventing a new one (e.g. a dedicated least-privilege role), since every sibling app already relies on the same shared `root` user for local dev.
2. **Migrations live in `packages/scan-ingestion/src/db/migrations/`** as plain numbered `.sql` files, schema-qualified throughout (`CREATE TABLE cqms.projects (...)`, `CREATE FUNCTION cqms.fn_upsert_project(...)`, etc.) — per the TECH_SPEC's locked "no ORM" decision:
   - `0001_init_cqms.sql` — `CREATE SCHEMA IF NOT EXISTS cqms;` + all 7 tables (`projects`, `scanners`, `runs`, `scans`, `reports`, `scan_findings`, `run_files`) with their indexes/constraints, verbatim from TECH_SPEC §2.3.
   - `0002_functions.sql` — `fn_upsert_project`, `fn_create_run`, `fn_finalize_run_status`, `sp_ingest_scan_result`, from TECH_SPEC §2.3a.
   - `0003_views.sql` — `run_file_stats`, `project_run_summary`, `run_scan_summary`, `project_scanner_trend`.
   - `0004_seed_scanners.sql` — idempotent (`ON CONFLICT DO NOTHING`) seed of the 4 `scanners` rows (`fallow`, `code-smell-checker`, `code-smell-zen` all non-deterministic; `linter` deterministic — per ADR/TECH_SPEC §2.5's "linter needs no LLM judgment" decision).
   - One correction against the TECH*SPEC draft, caught while writing the SQL: `sp_ingest_scan_result`'s body originally showed a bare `PERFORM fn_finalize_run_status(p_run_id);` call — this is in fact valid PL/pgSQL as written (`PERFORM` discards a function's return value in any PL/pgSQL block, procedure or function alike; `CALL` is only for invoking other \_procedures*). No wrapper needed — flagging this here because an earlier pass at this file briefly introduced an unnecessary `CALL`-based wrapper procedure before catching that the original TECH_SPEC syntax was already correct.
3. **Minimal migration runner** (`packages/scan-ingestion/src/db/runMigrations.ts`) — no migration framework/dependency added. A single `pg.Client`, a `cqms.schema_migrations(filename, applied_at)` tracking table (created by the runner itself on first run, inside the `cqms` schema), each pending `.sql` file applied inside its own `BEGIN`/`COMMIT` (rolled back on failure, not recorded as applied) via `node`'s native multi-statement simple-query support — confirmed this correctly handles multi-statement files including `$$`-dollar-quoted function bodies. Run via `node --env-file-if-exists=../../docker/local/.env --env-file-if-exists=.env --experimental-strip-types ./src/db/runMigrations.ts` (`pnpm run migrate`), matching the exact `--env-file-if-exists` layering convention `apps/api-server`/`apps/api-server-fast` already use for shared-then-local env overrides, and the same `node --experimental-strip-types` (no `tsx`/`ts-node` dependency) convention `packages/ts-configs/generate.ts` already established for standalone TS scripts in this monorepo.
4. **Env**: Zod-validated (`env.schema.ts`, `z.object({...}).parse(env)`) per the repo-wide Zod convention — deliberately not the hand-rolled parser `apps/api-server-fast/src/config/env.util.ts` uses (that predates the now-locked convention). `packages/scan-ingestion/.env` overrides only `DB_NAME=cqms_db` and `DB_PASSWORD` on top of the shared `docker/local/.env` — discovered empirically that the shared file's own `DB_PASSWORD=root` is a stale placeholder (the container's real `POSTGRES_PASSWORD` is a generated value), which every existing app's local `.env` already silently corrects the same way; this package's `.env`/`.env.example` now say so explicitly rather than repeating the silent-override pattern without comment.
5. **`packages/scan-ingestion` itself is only scaffolded to the depth this step needs** — `package.json` (name, `pg`/`zod` deps, `migrate` script), a minimal standalone `tsconfig.json` (`noEmit` + `allowImportingTsExtensions`, not yet wired into `packages/ts-configs/generate.ts`'s pipeline). The full standalone quality gate (fmt/lint/test parity with `packages/ui`/`packages/api`, per ADR-004's recipe) and the actual `ingestReport()`/Zod report schema/CLI wrapper are step 4's scope, not this one's.

## Consequences

- `cqms_db`/`cqms` schema exist and are fully verified end-to-end: all 8 tables (7 + `schema_migrations`), 4 functions/procedure, 4 views, and 4 seeded scanner rows confirmed via `psql`, plus a manual smoke test exercising `fn_upsert_project` → `fn_create_run` → `sp_ingest_scan_result` (report + finding + file-inventory insert + run-status finalization) end-to-end against live Postgres — findings/report/run-status all landed correctly, `project_run_summary`/`run_scan_summary` views returned correctly joined data, and cascade deletes cleaned up correctly. The throwaway smoke-test script itself was deleted after verification — step 4 builds the real TypeScript-level tests against this schema.
- Re-running `pnpm run migrate` is confirmed idempotent (all 4 migrations correctly skipped as already-applied on a second run).
- Everything else in CQMS (steps 4–9) reads/writes through this schema exclusively; no route or job reaches `apps/api-server` (TECH_SPEC §2.4 decision #4 reconfirmed).

## Verification performed

`docker exec postgres_container psql -U root -d cqms_db` — confirmed `\dt cqms.*` (8 tables), `\df cqms.*` (4 functions/procedure), `\dv cqms.*` (4 views), seeded `cqms.scanners` rows with correct `deterministic`/`supports_diff_scope` flags. Manual smoke test of the full `fn_upsert_project` → `fn_create_run` → `INSERT INTO cqms.scans` → `CALL sp_ingest_scan_result` path, verified against `cqms.runs`/`cqms.scans`/`cqms.reports`/`cqms.scan_findings`/`cqms.run_scan_summary`/`cqms.project_run_summary`, then cleaned up. `npx tsc --noEmit -p tsconfig.json` clean on the new package's TS files. `pnpm run migrate` re-run confirmed idempotent.
