# ADR-005: Generic `Form` component in `packages/ui`

**Status:** Accepted

## Context

TECH_SPEC §2.10 calls for a generic `Form` component in `packages/ui`, parallel to `Table`: the same "the component knows how to render itself from declarative config" philosophy (`columns` for `Table`, `fields` for `Form`), and `Form` must be exactly as agnostic to where its `fields` came from as `Table` already is about `columns` — whether hand-authored (CQMS's own `new-project`/`trigger-scan` forms) or computed server-side. This is Implementation Plan step 2, built on the `useStore.hook.ts` primitive `Table` already established (ADR-001) — no new dependency.

Two decisions were corrected mid-implementation, before any code was written for them, based on direct user direction:

1. **`<Form>` (navigation), not `useFetcher().Form`, by default.** The original TECH*SPEC draft suggested `useFetcher()` uniformly, citing `usePersistCookieAction.hook.ts` as precedent. Checked against React Router's own `Form` vs. `useFetcher()` decision guide directly (not assumed): the documented criterion is whether the URL \_should* change. CQMS's own consumers — creating a project, triggering a scan (which redirects to the run-detail page) — are exactly the "significant context shift" case the guide names `<Form>` for, not the "stay on this list, don't navigate" case `useFetcher()` is for. `usePersistCookieAction`'s use of `useFetcher()` was correct for _that_ case (a background cookie write with no navigation) but was the wrong precedent for a generic create/edit/view form component. `Form` now defaults to RR7's native `<Form>` + `useNavigation()`; `useFetcher().Form` is kept as an explicit opt-in (`submission: 'fetcher'`) for a future non-navigating use case, not the default.
2. **`mode: 'create' | 'edit' | 'view'` is a first-class part of the contract**, not just create. In `view` mode every leaf field is forced disabled and the footer (submit/cancel) isn't rendered at all — the form is read-only, full stop. In `edit` mode the submit button is disabled and submission is blocked client-side unless at least one field's value actually differs from the pristine snapshot captured at mount — so an unmodified edit form never triggers a write. CQMS's Phase 1 routes (`new-project`, `trigger-scan`) only exercise `mode: 'create'`; `edit`/`view` have no real CQMS consumer yet, so they're covered by `Form.test.tsx`'s integration tests directly rather than by a real route.

## Decision

1. **Store pattern mirrors `Table` exactly** (per the `store-pattern` skill, which is MANDATORY reading before touching this kind of state): one external store (`FormState<TValues>` — `values`, `errors`, `initialValues`, `mode`) behind a non-generic `createContext` erased at the provider boundary and restored via a generic cast on read (same technique as `TableDataContext`). Components only ever call selector hooks (`useGetFieldValue`, `useGetFieldError`, `useGetFormMode`, `useGetIsFormDirty`) or action hooks (`useSetFieldValue`, `useSubmitForm`) — never `formStore.get()`/`.set()` directly. `Form.component.tsx` composes `FormProvider` and delegates all actual rendering to a private `FormBody`, exactly as `Table.component.tsx` composes `TableDataProvider` and delegates to `TableContent`.
2. **Recursive field tree, one walker, reused three ways.** `FieldNode<TValues>` is a discriminated union: `group | row | tab | <leaf>`. `flattenFields.util.ts` is the single recursive walker; `getInitialValues`, `validateFields`, and the edit-mode dirty check all consume its flattened output rather than each re-implementing the recursion (the second draft of the _reference_ implementation this was studied against — `/home/lucio/workspaces/control-business-ui-ts/src/components/Form`, a different, unrelated project — had exactly this bug: `FormFields.tsx`/`getInitialData.ts`/`validateFields.ts` each independently reimplemented `group`/`row` recursion).
3. **Leaf types dispatch through a registry (`FormField.constants.ts`), not a switch.** `text | email | password | textarea | number | boolean | select | radio | date | datetime | custom`. Each concrete leaf component (`TextField`, `NumberField`, ...) is generic over its own `TValues`; the registry itself is typed as `Record<type, AnyFieldComponent>` with each entry cast at the registry boundary — the one intentional, narrowly-scoped `any`-adjacent cast in the whole component, confined to that single indirection point.
4. **Leaf renderers reuse the existing design system — verified by reading the real component prop types, not assumed:** `boolean` → `Checkbox` or `ToggleSwitch` (`variant` prop); `select` → `VirtualSelect` (static `options`, not the fetch-mode path `SelectFilterInput` uses); `radio` → `RadioOptionGroup`. `text`/`number`/`date` needed genuinely new bare inputs: checked `TextFilterInput`/`NumberFilterInput`/`DateFilterInput` first, confirmed they're tightly coupled to the filter-operator system (`operator`, `DataKey<TData>` props) and not extractable into a shared primitive without touching working Table filter code for uncertain benefit — so `TextField`/`NumberField`/`DateField` are new, but reuse the existing `filterBaseStyles` design tokens (`packages/ui/src/design-system/tokens/filters.stylex.ts`) and `NO_AUTOFILL_INPUT_PROPS` constant rather than inventing new input chrome.
5. **`VirtualSelect` has no native form control at all.** `SelectField` mirrors its current selection into hidden `<input type="hidden">` elements so RR7's `Form`/`fetcher.Form` still submits real `FormData` for it — everything else (native inputs, checkboxes, radios) participates automatically via `name`.
6. **`noValidate` on the `<form>` element**, discovered empirically via a failing test: leaf inputs still carry native `required`/`min`/`max` attributes for accessibility, but without `noValidate`, native HTML5 constraint validation intercepts the click _before_ the `submit` event — and therefore before `handleSubmit`/`preventDefault` — ever fires, silently defeating both the required-field client validation and the edit-mode dirty gate. RR7's own `Form` implementation calls the consumer's `onSubmit` first and checks `event.defaultPrevented` before doing its own submission — confirmed by reading its source directly — so `noValidate` plus our own JS gate is what makes that mechanism actually reachable.
7. **Client validation (`validateFields.util.ts`) is hand-rolled, not Zod**, per TECH_SPEC §2.10's reasoning: it's progressive-enhancement-only instant feedback, and the consuming route's action + Zod schema remains the sole authority — duplicating Zod client-side would mean maintaining the same rules in two places for no gain, since the server can't be bypassed regardless.
8. **`serverErrors` (from a route's `useActionData()`) flows back into the same store** via a `FormProvider` prop, re-synced with a `useEffect` keyed on the prop's identity — mirroring exactly how `TableDataProvider` re-syncs an incoming `dataState` prop into its own store on change.

## Consequences

- `packages/ui` gains `Form`, fully covered by `Form.test.tsx` (registry dispatch across every leaf type, group/row/tab nesting, required-field validation blocking submission, view-mode read-only enforcement, edit-mode dirty-gated submission) plus dedicated unit tests for `flattenFields`/`getInitialValues`/`validateFields`/`isFormDirty`. All exercised through `react-router`'s `createRoutesStub`, so the real RR7 `<Form>`/`useNavigation()`/action wiring is what's under test, not a mocked stand-in.
- Native checkboxes are omitted from `FormData` entirely when unchecked (standard HTML behavior) — any consuming action's Zod schema must treat an absent boolean field as `false`, not error on a missing key.
- `INVENTORY.md` updated with the new `Form` component entry.
- CQMS's `new-project`/`trigger-scan` routes (Implementation Plan step 8) are the first real consumers and will only exercise `mode: 'create'` — `edit`/`view` remain proven only by this component's own tests until a future CQMS or other-app route needs them.
