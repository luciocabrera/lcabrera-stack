# ADR-017: RBAC schema + username/password authentication core

**Status:** Accepted

## Context

Phase 3 (see the approved phase plan) requires every CQMS table to carry
audit fields (`created_by`/`edited_by`), every DB write to be permission-
checked inside Postgres, and the app to know who is acting. Until now the
app had no identity at all — anyone who could reach the internal URL
could register projects and trigger scans, and nothing recorded who did
what. Decisions confirmed with the user before this step (not re-argued
here): username + **password** login (not a passwordless picker or OS-user
mapping), roles **plus per-instance grants**, enforcement via a
`p_user_id` parameter checked by a shared DB function, and full scope this
phase including a management UI (a later step).

## Decision

### 1. Schema (migration `0008_rbac.sql`) — Postgres owns the model

`cqms.users`, `cqms.roles`, `cqms.permissions` (the full
`action × resource_type` matrix: create/read/update/delete/execute ×
project/run/scan/scanner/user/role/workspace — a reference table like
`cqms.scanners`, so new resource types are data plus a CHECK widening,
not a redesign), `cqms.role_permissions`, `cqms.user_roles`, and
`cqms.resource_grants` (a narrow allow on ONE resource row, granted to a
user or a role, with a `CHECK` enforcing exactly one grantee).

`cqms.fn_assert_permission(p_user_id, p_action, p_resource_type,
p_resource_id DEFAULT NULL)` is the single deny-by-default gate: unknown
user → deny; disabled/soft-deleted user → deny; role permission =
type-wide allow; per-instance grant checked only when a resource id is
passed. Denials `RAISE EXCEPTION` with errcode `42501`
(`insufficient_privilege`) and a human-readable reason — the TS layer
surfaces that message to the UI verbatim, per the explicit "return a
message to the API explaining the rejection" requirement. Migration 0009
(ADR-018) wires this into every write/execute function; this step ships
the gate plus its TS face, `queries/checkUserPermission.util.ts` (a
non-throwing wrapper returning `{allowed, reason}` for UI route gating).

Audit-depth convention applied as decided: entity tables get the full
set (`created_by/created_at/edited_by/edited_at/enabled/deleted_at`);
pure junctions (`role_permissions`, `user_roles`) are lean
(`created_by/created_at`) — added and removed, never edited.

**Password hashes never leave the DB except for login**: `cqms.v_users`
(the view all normal reads go through) excludes `password_hash`;
`fn_get_user_credentials(p_username)` is the single hash-returning path
and yields no row for disabled/deleted users, so authentication fails
before any hash comparison.

**Seeds**: the permission matrix; roles `admin` (everything),
`developer` (full project/run/scan/workspace + read scanner), `viewer`
(read-only); user `admin` with default password `admin` — **change it
after first login** (internal tool, but still a known default); user
`system`, the scan-orchestrator's actor identity, whose `password_hash`
is a sentinel (`!no-login!`) that `isPasswordValid` structurally rejects
— an account that can act but never log in.

### 2. Hashing — `node:crypto` scrypt, zero new dependencies

`src/auth/hashPassword.util.ts` / `isPasswordValid.util.ts`
(scan-ingestion): scrypt with default cost params, 16-byte random salt,
64-byte key, output `<saltHex>:<hashHex>`, comparison via
`timingSafeEqual`. Chosen over bcrypt/argon2 because it adds no
dependency and is entirely adequate for an internal tool; malformed
stored hashes return `false` rather than throwing (that is what makes
the `system` sentinel non-loginable). The seeded admin hash in the
migration was generated by this exact util, not hand-rolled.
(`isPasswordValid` rather than `verifyPassword` — the repo's
boolean-name lint rule requires the `is` prefix.)

### 3. Session + gate (admin_system)

React Router's built-in `createCookieSessionStorage` (no new
dependency): httpOnly, `sameSite=lax`, browser-session lifetime, signed
with `SESSION_SECRET` (Zod schema with a deliberate dev-only default so
local boot needs no setup — set a real value beyond local use). The
storage initializes at module level rather than a lazy getter —
`getPool`'s lazy-singleton shape trips
`unicorn/no-top-level-assignment-in-function` here, and this module is
only evaluated server-side where eager env reading is safe.

`requireUser({ request })` is the gate every CQMS surface calls first —
chosen over the `v8_middleware` flag as the established pre-middleware
pattern. It re-validates the session's `userId` against `cqms.v_users`
on every call, so a user disabled after login is kicked on their next
request, not at cookie expiry; failures throw a redirect to
`/login?redirectTo=<original destination>`.

**Where it is wired — and why twice**: the cqms layout loader gates
every child page view (nested loaders all run per navigation), but React
Router runs a POST's action BEFORE any loader, so each cqms action
(`new-project`, `edit-project`, `trigger-scan`) calls `requireUser`
itself. The `_action/browse-directory` resource route — which lists real
directories on this machine — went from a bare re-export of the shared
loader to a gated wrapper. `_action/persist-cookie` (theme flags) stays
public deliberately.

`/login` is a normal Form-component route (username + password fields,
`password` field type): one generic "Invalid username or password." for
both unknown-user and wrong-password (no account-probing oracle), an
open-redirect guard on `?redirectTo` (same-origin absolute paths only),
and a bounce-to-app loader for already-authenticated visitors. `/logout`
is action-only (POST) so a crawler or prefetch can never end a session.

## Consequences

- Every subsequent Phase-3 step has an actor: audit columns get real
  `created_by` values, write functions can check `fn_assert_permission`,
  and the orchestrator acts as `system`.
- All existing CQMS pages/actions now require login; the seeded
  `admin`/`admin` credential is the only way in until Step 10's user
  management UI lands.
- The scan-orchestrator's WebSocket endpoint (`/ws/runs`) remains
  unauthenticated this phase — a known, accepted limitation recorded
  here.
- Anything that later needs the acting user server-side reads it from
  `requireUser`'s return value (the cqms layout loader also exposes it
  to child routes via matches).

## Verification performed

- Migration 0008 applied cleanly to the live `cqms_db`; re-run skipped
  (idempotent runner); seeds verified by the tests below.
- `packages/scan-ingestion`: 76/76 tests green, including 18 new real-DB
  tests — hash/verify round-trip + sentinel rejection;
  `authenticateUser` (valid, wrong password, unknown user, disabled
  user, and the seeded `system` sentinel); `getUserById` via `v_users`
  (no `password_hash` key, soft-deleted → undefined);
  `checkUserPermission` (viewer role allow/deny with the DB's reason
  text, per-instance grant allowing one resource id and not another,
  unknown user).
- `apps/admin_system`: 23/23 tests green (3 new `requireUser`
  redirect-path tests), typecheck + lint clean in both packages.
- **Live E2E against the dev server** (curl, real session cookies):
  unauthenticated `/cqms/projects` → 302 to
  `/login?redirectTo=%2Fcqms%2Fprojects`; wrong password → 200 with
  "Invalid username or password." in the response; `admin`/`admin` →
  302 with an httpOnly `__cqms_session` cookie; authenticated request →
  200; authenticated visit to `/login` → bounced to the app; `POST
/logout` → cookie expired (Epoch) + redirect to `/login`;
  `_action/browse-directory` → 302 without a session, 200 with one.
