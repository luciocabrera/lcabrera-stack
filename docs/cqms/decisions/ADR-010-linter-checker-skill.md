# ADR-010: `linter-checker` skill — the one fully-deterministic scanner

**Status:** Accepted

## Context

Implementation Plan step 6, per TECH_SPEC §2.5: a 4th scanner wrapping `oxlint` + the custom-rules `eslint` pass, distinguished from the other three by needing **zero LLM judgment** — a lint violation already carries an unambiguous rule, location, and human-readable message straight from the tool. Ground-truth research before writing anything confirmed:

- `apps/admin_system` is a real scaffolded app (not just a `generate.ts` reference), giving a concrete oxlint/eslint target to sample real output shapes from, rather than working from `TECH_SPEC.md`'s own (undated) samples.
- `npx oxlint`/`node_modules/.bin/oxlint` at the repo root is **shadowed by `vite-plus`'s own LSP-only wrapper** — it refuses to lint and prints a "run `vp lint`" message. Real oxlint output can only be reached either by resolving the nested `oxlint` package's own `dist/cli.js` directly (bypassing `vp`, and losing whatever extra rule config `vp lint` merges from each app/package's own `vite.config.ts` `lint:` block — confirmed empirically as a real difference: 110 rules via `vp lint` vs. 95 via the raw binary) or through `vp lint --format json` itself. **Decision: go through `vp lint --format json`**, not the raw binary, so the deterministic script's findings match what a developer actually sees, not a reduced rule set.
- The custom-rules eslint pass (`eslint . --config eslint.config.mjs --format json`) only exists for apps with their own `eslint.config.mjs` (`apps/react-router`, `apps/admin_system` — confirmed via `createCustomRulesLintConfig`'s actual call sites) — most `packages/*` have no such file. The script must skip this pass gracefully when absent, not error.

## Decision

1. **Directory shape mirrors `fallow-code-checker` exactly** — `.github/skills/linter-checker/{SKILL.md, scripts/generate-linter-report.mjs}`. Unlike `fallow-code-checker` (whose script does only the deterministic raw-scan half, leaving triage/severity/report-writing to the LLM), **this script does everything**: lint invocation, raw-artifact merge, `report.json` construction, `report.md` rendering, saving all three files, and the CQMS ingestion call — because none of those steps need LLM judgment here. `SKILL.md` is accordingly thin, matching TECH_SPEC's own framing ("mostly 'run the script, it produces all three artifacts unattended, report the saved paths'").
2. **`linter.raw.json`** mirrors `fallow.raw.json`'s own `"kind": "combined"` convention: `{ kind: 'combined', oxlint: {...}, eslint: [...] }` (`eslint: []` when the scope has no custom-rules config).
3. **Finding mapping**, per TECH_SPEC §2.5: oxlint `severity: "error"|"warning"` and eslint `severity: 2|1` → `HIGH`/`MEDIUM` (fixed two-tier table — no BLOCKER/LOW/NIT nuance is derivable mechanically); `confidence: "high"` always; `effort: "small"` always; `rule_id`/`location_path`/`location_hint`/`why` taken directly from each tool's own output; `fix` uses oxlint's own `help` text where present, falling back to `"Address per rule: ${ruleId}."` for eslint (which has no equivalent field). `report.json` **is** the report — there's no separate LLM-authored Markdown to reconcile it against, so `report.md` is templated mechanically straight from `report.json`'s own data (severity counts, top-rule-by-frequency for `top_risk`/`first_3_actions`, a prioritized queue grouped by rule).
4. **A real bug caught by actually running the script against a real target (`apps/react-router`), not by inspection**: the initial `finding_id` hash (`sha1(rule_id, location_path, location_hint)`) collided for real — ESLint's `perfectionist/sort-imports` rule reports **two distinct messages at the identical line:column** (e.g. "Expected X before Y" and "Extra spacing between X and Y" on the same import statement), which produced identical hashes and violated `scan_findings`'s `(scan_id, finding_id)` unique constraint, failing ingestion outright on the very first real run. Fixed by including the message text itself in the hash input. This is exactly the kind of thing `report.schema.ts`'s own Zod parse (or the DB constraint) would catch at ingestion time regardless — but catching it by actually running the tool end-to-end, rather than only unit-testing the mapping function in isolation, is what surfaced it before it could affect a real user-triggered run.
5. **`allowed-tools:` kept minimal** — just `Bash(node:*), Read` (no `bash:*`/`git:*`/`vp:*`/`npx:*` needed directly in the skill's own frontmatter, since the script itself is the one thing invoked, and it shells out to `vp`/`eslint`/`git`/`node` internally via `child_process` — those sub-invocations aren't separately gated by the _skill's_ frontmatter the way a direct `!bash` directive would be). One new `.claude/settings.json` allowlist entry, matching the existing trailing-wildcard convention.
6. **`cqms.scanners`' seed row for `linter`** (already inserted in ADR-006, ahead of this skill actually existing) needed no changes — `skill_path = '.github/skills/linter-checker'` and `deterministic = true` already matched what got built here, confirmed by direct query after the fact rather than assumed.

## Consequences

- `scripts/validate-skills.cjs` reports 10 skill directories validated (was 9) — `code-smell-shared` still correctly skipped as a non-skill directory.
- Per TECH_SPEC §2.5's own framing, this scanner's execution branch in the future background-job orchestrator (step 9) is simply `scanner.deterministic ? runDeterministicScript() : runSkillAgent()` — `linter-checker` is the `runDeterministicScript()` case, needing no Agent SDK involvement at all (unlike the other three, which step 7's `packages/agent-runner` will drive).
- Verified end-to-end against two real, different targets: `apps/react-router` (57 real findings — 56 `HIGH`, 1 `MEDIUM`, dominated by `perfectionist/sort-imports`) exercising both the oxlint and custom-rules-eslint passes together, and `packages/scan-ingestion` (0 findings, no `eslint.config.mjs` present) exercising the graceful-skip branch. Both runs' DB rows were inspected directly via `psql`, confirmed correct, then cleaned up (these were verification runs, not user-requested scans — the user can run the skill for real now that it's built).

## Verification performed

`node scripts/validate-skills.cjs` — clean, 10 skills. Two real end-to-end runs of `node .github/skills/linter-checker/scripts/generate-linter-report.mjs <scope>` (`apps/react-router` and `packages/scan-ingestion`), each producing real `linter.raw.json`/`report.json`/`report.md` and successfully ingesting into the live `cqms_db` (57 and 0 findings respectively), verified via direct Postgres queries against `cqms.runs`/`cqms.scan_findings`, then cleaned up. The `finding_id` collision bug was caught and fixed during the first of these two runs, not before.
