# ADR-007: `packages/scan-ingestion` core — `ingestReport()`, the `report.json` contract, and the CLI wrapper

**Status:** Accepted

## Context

Implementation Plan step 4, built on ADR-006's schema. TECH_SPEC §2.4 specifies a single shared function, `ingestReport()`, with two callers (each skill's final step via a CLI wrapper, and `admin_system`'s background job importing it directly) — "not two divergent code paths." Before writing any code, research turned up ground truth that changed the design in real ways (see below), rather than assuming `SCHEMA_V1.md` already defined a JSON contract.

## Decision

1. **`SCHEMA_V1.md` is a Markdown contract, not a JSON one — confirmed by reading it directly.** No `report.json` exists anywhere in this repo today; the three existing skills (`fallow-code-checker`, `code-smell-checker`, `code-smell-zen`) only ever emit `report.md`. This package is _defining_ the `report.json` contract Step 5 will retrofit those skills to satisfy, not parsing something that already exists. `report.schema.ts`'s shape is modeled on `cqms.scan_findings`'/`cqms.reports`' actual `NOT NULL`/`CHECK` constraints (TECH_SPEC §2.3a's explicit instruction — Postgres owns per-field validity, the Zod schema is a thin top-level check), not a field-by-field transcription of `SCHEMA_V1.md`'s prose "required" list. Its top-level shape (`blocker_count`/`high_count`/... flat) deliberately matches `sp_ingest_scan_result`'s `p_report_metadata` parameter almost verbatim rather than `SCHEMA_V1.md`'s nested `findings_count_by_severity`, so `ingestReport()` needs no reshaping step in between.
2. **Two real correctness issues found before writing the skill-facing schema, not after:**
   - Real, already-generated `report.md` files (`code-smell-checker`, `fallow-code-checker`) use `status: resolved` extensively — neither `SCHEMA_V1.md` nor `cqms.scan_findings`'s `CHECK` constraint accepts it (only `open|in-progress|done|deferred`). `scanFindingSchema` rejects `resolved` on purpose; **Step 5 must map it to `done` when generating `report.json`**, flagged here loudly so it isn't missed when that step is built.
   - `sp_ingest_scan_result` bulk-inserts findings via `jsonb_to_recordset`, which does **not** apply a column's `DEFAULT` for an absent/`null` JSON key — it inserts SQL `NULL`. `verification_steps`, `extra`, and `finding_kind` are all `NOT NULL DEFAULT ...` columns, so an omitted key in a scanner's finding JSON would fail the constraint instead of silently getting the default. `scanFindingSchema`'s own `.default([])`/`.default({})`/`.default('single_location')` is what keeps the bulk insert correct regardless of what a scanner's emission logic omits — this is a real bug that would only have surfaced once Step 5 produced its first real `report.json` missing one of these keys, not something the DB layer alone would have caught.
3. **`ingestReport()`'s flow matches TECH_SPEC §2.4/§2.3a exactly**: Zod-parse `report.json`, read `report.md` verbatim, read the raw artifact if given (only `fallow` populates `rawJsonPath` today), resolve/create the run+scan (`resolveScan.util.ts` — UI path looks up the existing `(run_id, scanner_id)` scan row created by the trigger-scan action; ad hoc path resolves the git root via `resolveProjectPath` then calls `fn_upsert_project`/`fn_create_run` and inserts the `scans` row directly), one `UPDATE` for `raw_json`/`health_metrics` (not `sp_ingest_scan_result` parameters), then one `CALL cqms.sp_ingest_scan_result(...)` — no hand-assembled multi-INSERT transaction logic in TypeScript.
4. **`getPool.util.ts` is a lazy singleton**, not a per-entry-point `Pool` constructed once at startup (the `apps/api-server`/`apps/api-server-fast` convention) — this package is a _library_ with multiple, independent entry points (CLI wrapper, `admin_system`'s job code, migration runner), none of which is "the" single place to own a `Pool`'s lifecycle.
5. **A real, non-obvious import-convention exception, caught by actually running the CLI, not by `tsc`/`vitest`:** this package has two genuinely different execution contexts — Vite/Vitest/tsc (which understand the `@repo/scan-ingestion/*` self-referencing alias via `tsconfig.app.json` paths and `vite.config.ts`'s `resolve.alias`, matching `packages/ui`'s own convention), and plain `node --experimental-strip-types` (`db/runMigrations.ts`, `cli/ingest.cli.ts`, and anything they transitively import) — where **neither** tsconfig paths nor Vite's alias apply, since there is no bundler or tsc in that execution path at all. `ingest.cli.ts` and `ingestReport.ts` (loaded by both the CLI and Vitest) use **relative** imports for exactly this reason; only `ingestReport.test.ts` (Vitest-only, never bare-node) safely uses the alias. First attempt used the alias everywhere per the established `packages/ui` convention; it typechecked and passed tests cleanly, then failed immediately at real CLI runtime with `ERR_MODULE_NOT_FOUND` — fixed by actually running the CLI end-to-end against a real temporary git repo, not just trusting the type/test gate.
6. **Standalone quality gate mirrors `packages/api`'s recipe (ADR-004)** — `createNodeTsConfig` (genuinely Node-only: `pg`, `fs`/`path`, `git` via `child_process`, zero DOM/`vite.client` usage, confirmed by grep, unlike `packages/api` which surprisingly needed `createAppTsConfig`), with `include: ['src', 'vite.config.ts']` overridden since `createNodeTsConfig`'s default include (`['vite.config.ts']` only) is designed for an app's Node-context sibling config, not a package whose own `src/` needs typechecking. `createApiLintConfig` (no React/StyleX). The `migrate` script and the `test` task both load env via `--env-file-if-exists=../../docker/local/.env --env-file-if-exists=.env`, matching `apps/api-server`/`apps/api-server-fast`'s exact layering — needed so integration tests reach the real `cqms_db`.

## Consequences

- `packages/scan-ingestion` is CQMS's entire persistence/API backend, fully standalone-quality-gated (fmt/lint/typecheck/test) and verified against the real, live `cqms_db` — no mocked `pg` client anywhere in its test suite.
- Step 5 (adding `report.json` emission to the three existing skills) has an exact target contract to build against, plus an explicit, documented requirement to map `status: resolved` → `done` during emission — this ADR is the place that requirement is recorded so it isn't missed.
- The CLI wrapper (`node .../cli/ingest.cli.ts --skill=... --run-dir=... --local-path=...`) is proven end-to-end against a real temporary git repository and the real schema, matching the exact invocation shape TECH_SPEC §2.4 specifies for each skill's final step.
- Any future file in this package that's meant to run via plain `node` (not just Vite/Vitest) must use relative imports for anything it transitively pulls in — the self-referencing alias is for this package's _other_ consumers (other packages/apps), not for its own bare-node entry points.

## Verification performed

`vp fmt --check .`, `vp lint .`, `tsc --noEmit -p tsconfig.app.json`, `vp run test` — all clean (5 test files, 30 tests, all against the real `cqms_db`, no mocks). Additionally: the CLI wrapper run directly end-to-end against a real temporary git repository (`git init` + a real commit), verified via direct Postgres query that the project/run/scan/finding rows landed correctly, then cleaned up.
