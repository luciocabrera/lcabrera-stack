lcabrera-stack · the product

Two products, one repository

The repository ships two things, split by who installs them. An application installs the application stack: a data grid, the wire contract between browser and server, and a safe query layer. Another repository installs the toolchain: configs, gates, lint rules, and the agent setup that runs this repository, packaged so it can run someone else's.

The public packages are published to npm under @lcabrera/*. Internal ones stay under @repo/*, so an import line tells you which side of the product boundary you are on.

1 · The product lines

Split by consumer, not by build shape

A package belongs to a line because of who installs it. The UI library publishes TypeScript source and the toolchain publishes plain .mjs, yet each sits where its consumer does. A capability that serves neither consumer is a signal to stop, not to add a package.

Application stack

Installed by an application

Rendering, querying and serving data: the grid a user works in, the contract between the two ends, and the query layer behind it.

Repository toolchain

Installed by a repository

The standards a repository runs on: TypeScript and Vite+ configs, lint rules, gates, git hooks, and the agent instructions that come with them.

Internal harness

Never published

The showcase app that puts the packages under load, the eval history store, and this repository's own config roster. When app convenience and package cleanliness conflict, the package wins.

3 · The runtime boundary

A client-safe package may only depend on client-safe packages

The browser half and the server half used to be one package. The cost showed up as the Postgres driver riding into every consumer of the UI library, because it needed two fetch helpers. They are now split by runtime, and each tsconfig denies the other side's types. Try an import the rules forbid.

Runs anywhere
@lcabrera/utils

Pure functions. No side effects, no dependencies.

Browser-safe
@lcabrera/api@lcabrera/ui

No node types. Fetch, validation and the grid.

Node only
@lcabrera/server@lcabrera/node

No DOM lib. Postgres, secrets, process lifecycle.

4 · Who it is for

Requirements written in each user's words

A persona earns a place by having a different definition of "it works". Each requirement in the register is written for exactly one of them, names the packages it judges, and declares whether it is met. A change that earns a requirement flips its state in the same commit. Pick a persona.

Current state of each requirement: docs/product/requirements.

5 · The harness

The showcase app puts the packages under load

A React Router SSR app, and the only workspace that depends on several packages at once, which makes it the place cross-package integration is proven. It never holds a guarantee a package relies on: a package must work from outside this repository, where none of the monorepo's wiring exists.

Large tables

Virtualized and infinite-scroll grids over seeded Postgres data, including a wide table with many column types, to keep render cost honest.

Grouping and summaries

Group rows into a report, fold levels, drill into a group, and put a dimension across the top of a summary. Grouping runs as SQL on the server.

Editing

Create, view, edit and delete orders through route loaders and actions, with validated input and no data fetching in effects.

Eval dashboard

Pass rates and run history from the agent eval suites, served as aggregates only, so no transcript leaves the database.
