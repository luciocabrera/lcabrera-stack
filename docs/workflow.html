lcabrera-stack · how the work gets done

Interlocked agent delivery

In a signal box, an interlocking makes a dangerous route impossible to set, however confident the signaller feels. This repository treats agent-written code the same way: every step from issue to main is gated by something that can say no, and the agent that writes a change is never the one that certifies it.

A personal TypeScript monorepo by Lucio Cabrera, used to practise agent-driven delivery end to end. Every mechanism below links to the file that implements it.

Instructions live in gitOne AGENTS.md, symlinked as CLAUDE.md, GEMINI.md and Copilot's instructions. Path-scoped rules load only for the files they govern.
The certifier is blindA fresh reviewer agent sees the diff and the acceptance criteria. It never sees the builder's reasoning.
Agents are evaluated tooSkills, subagents and rules have their own eval suites, run in CI, with pass rates reported as confidence intervals.
1 · The route

From issue to merged, one gate at a time

Select a stage, or step through with the buttons. Each one names who acts, what they are allowed to do, and the mechanism that stops the next stage when this one fails.

2 · Who sees what

The isolation rule

An agent that reads its own diff knowing what it meant reads it for confirmation, not refutation. So the reviewer is denied the builder's reasoning by construction, and the orchestrator, which sees everything, cannot edit the change. Pick a role to see its view.

3 · The round loop

Three rounds, then a human decides

The builder receives the verifier's findings; the verifier never receives anything the builder said. Each round starts a fresh verifier with no memory of the last, so it re-checks every criterion rather than only the one that failed before. Play out a run.

4 · The evidence standard

A green run proves nothing until it has been red

A rule that never loaded reports the same clean pass as correct code. So a PASS needs at least one acceptance criterion backed by a fail→pass pair: the verifier plants a violation of that specific criterion, watches the gate fail, reverts, and watches it pass. Planting a debugger statement only proves the linter runs. The plant has to target the criterion.

Example from the fixture issue: "clampNumber returns max when value > max"
  1. Confirm a clean tree
    $ git status --porcelain (empty)
    precondition
  2. Plant a violation of this criterion
    - if (value > max) return max; + if (value > max) return value;
    plant
  3. Run the gate and record the failure
    $ vp run test ✗ clamps a value above max expected 10, received 12
    exit 1
  4. Revert and prove the tree is clean again
    $ git checkout -- src/ && git status --porcelain (empty)
    revert
  5. Run the same gate on the clean tree
    $ vp run test ✓ clamps a value above max
    exit 0

The verdict is written to a JSON document with a fixed schema, posted as a PR comment that names the head commit, and validated by the Agent review verdict check. No workflow greps prose for "LGTM". See the verifier contract and the review verdict contract.

5 · Enforcement versus advice

What the harness enforces, and what it only asks

Prompt text is advice: an agent can misread it or drop it from context. Anything that must hold is moved into a hook, a git hook or a CI check, where it runs whether or not the agent remembers it.

blocks

Secrets guard

A Claude Code PreToolUse hook. It denies any read of a secret or .env file and any write that introduces a credential, before the tool runs. It returns a structured deny decision, because exiting with an error does not block a tool call.

Per-file autofix

A PostToolUse hook that runs the linter's fixer and the formatter on the one file the agent just wrote. It always exits 0, so it is a convenience, and every check it touches is also enforced later.

6 · Evaluating the agents

The verifier is tested against planted defects

If someone edits the verifier's prompt and it quietly stops catching a class of violation, nothing else would notice. So the repository keeps fixtures: a clean change, and copies of it with exactly one defect each. The eval runs the verifier's real prompt on each and checks it marks the right criteria not-met. Every fixture shares one small issue: a clampNumber utility with five acceptance criteria. Pick a fixture.

Every run writes a versioned envelope with each trial's tokens, cost and duration, scrubbed of secrets as it is written, and stores it in Postgres so pass rates can be compared across runs. A real failure in day-to-day work becomes a new task, tagged as an incident, and graduates to the regression set once the fix makes it pass reliably.

When does a pass rate count as a regression?

Model output varies, so one failed trial is not a regression and one passing trial is not proof. Each task runs several times. A task that passed every trial on main is flagged on a pull request when the share of failing trials reaches 2 in 3, and a pass rate is only reported once there are at least 6 counted trials, with a 95% Wilson interval. These thresholds live in one config file, not in code. Try it.
