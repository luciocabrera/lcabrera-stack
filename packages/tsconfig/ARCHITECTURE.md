# `@lcabrera/tsconfig` — architecture

Consumer-facing usage is [README.md](README.md). This file is for someone
changing the package.

## Why this package exists separately from `@repo/ts-configs`

The two names are close enough to confuse, so the boundary is worth stating
before anything else ([ADR-069](../../docs/decisions/ADR-069-publish-the-shared-toolchain.md)):

|                 | `@lcabrera/tsconfig` (here)   | `@repo/ts-configs`                            |
| --------------- | ----------------------------- | --------------------------------------------- |
| What it is      | the published package         | the private workspace that survives the split |
| Holds           | both factories and the writer | `tsconfig.entries.ts` plus a one-line runner  |
| `private`       | `false`                       | `true`                                        |
| Who consumes it | this repo, and any other repo | nothing — it is a task host, not a library    |

`packages/ts-configs` was **split**, not renamed. Everything generic moved here;
what stayed behind is this repo's own workspace roster, which a consumer must
never receive. That is why `vp run --filter @repo/ts-configs generate` is still
the command that regenerates this repo's configs, and why it did not change when
the package it calls became publishable.

## Layout

| File                     | Holds                                                                          |
| ------------------------ | ------------------------------------------------------------------------------ |
| `src/tsconfig.shared.ts` | `createAppTsConfig` / `createNodeTsConfig` and every compiler option they set  |
| `src/generate.ts`        | `renderTsConfig` (pure) and `writeTsConfigs` (the one effect in the package)   |
| `tsconfig.app.json`      | generated by `@repo/ts-configs` like every other workspace's — never hand-edit |

Nothing here names a workspace. Every `@lcabrera/*` string in `tsconfig.shared.ts`
is illustrative JSDoc, and that is the property that has to survive an edit: a
repo fact added to a factory default is a repo fact shipped to every consumer.
If a caller needs it, it is an option with a neutral default, not a constant.

## The one effect, and where it lives

`writeTsConfigs` is the only thing in the package that touches the world, and it
writes wherever the caller's entry table points. `TsConfigFileSystem` makes that
an argument with a `node:fs/promises` default rather than a hardwired import, so:

- the host owns the effect, and can dry-run, sandbox or virtualize it;
- `generate.test.ts` asserts what a run produces without a temp directory.

That default is itself covered — `generate.test.ts` mocks `node:fs/promises` and
asserts `mkdir`/`writeFile` are reached with the expected arguments. Without
that case, replacing the default with a no-op would leave every other test green
while the generator silently stopped writing anything.

## Rendering is a byte contract

Generated tsconfigs are committed in the repos that use this package, so
`renderTsConfig`'s output is compared against a tracked file on every run.
Changing the indent, the trailing newline, or the `JSON.stringify` replacer
would show up as a diff in every workspace of every consumer at once. It is
exported for that reason: a consumer whose build system does its own writing
needs to be able to produce the identical string.

`renderTsConfig` does **not** format the way a formatter would — short arrays
stay expanded. Running the repo's formatter after generation is part of the
documented workflow, here and in the README, and is why regeneration in this
repo is `generate` followed by `vp fmt .`.

## Publishing

This package is in the strictest tier (AGENTS.md §4, [`packages/CLAUDE.md`](../CLAUDE.md)):
no baselines, no scoped rule-offs, no inline disables, and a gitignored
`eslint-suppressions.json`. It builds to `dist` and swaps `exports` for
`publishConfig.exports` at pack time — a `.ts` file inside a consumer's
`node_modules` is not loadable at all
([ADR-060](../../docs/decisions/ADR-060-source-shipping-package-module-resolution.md)),
and this package's writer is _run_, not merely typechecked.

Adding an export means adding it to both maps; `vp run publish:verify` fails when
they disagree, and `vp run api-surface:verify` ratchets the type surface.
