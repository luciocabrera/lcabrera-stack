# @lcabrera/eslint-plugin Architecture

Custom ESLint rules, used across this monorepo and published for use outside it.

## Purpose

- Provide one canonical source for custom linting behavior.
- Separate global TypeScript rules from React-only rules via consuming app configs.
- Avoid rule drift between apps.

## Layout

- `src/index.ts` - the rule registry (`rules`) and the plugin object ESLint loads.
- `src/*.ts` - rule source files.
- `src/*.test.ts` - colocated `RuleTester` suite, one per rule (see Testing below).
- `src/component-files.ts` - shared definition of which filename suffixes mark a
  component file, used by every rule that gates on one.
- `src/file-names.ts` - shared parse of the `<base>.<suffix>.<ext>` shape, used
  by `filename-convention` and `domain-folder-filename`. Shared for the same
  reason as `component-files.ts`: a rule that parses filenames slightly
  differently from its neighbour goes quiet, not wrong.
- `dist/*.mjs` + `dist/*.d.mts` - `vp pack` output; what a consumer installs.
- `tsconfig.app.json` - generated by `@repo/ts-configs`; never hand-edited.

## Rule Scope Model

- Global-eligible rules:
  - `clean-import-paths`
  - `destructuring-for-functions`
  - `domain-folder-filename`
  - `filename-convention`
  - `merge-duplicate-imports`
  - `no-inline-type-imports`
  - `type-suffix-naming`
- React-only rules (enabled only in React app lint overrides):
  - `no-type-definitions-in-components`
  - `readonly-props`
  - `single-component-export`

`clean-import-paths` is global-eligible but deliberately **off** in the base
(non-React) config: those workspaces run TypeScript natively or compile with tsc
under NodeNext, where explicit extensions are required and stripping them would
fight the compiler.

## Testing

Every rule has a colocated `<rule>.test.ts` driving `@typescript-eslint/rule-tester`,
and `rules-have-tests.test.ts` fails the suite if one is missing.

That invariant is not bureaucracy. Four of these rules decide whether to run at
all from a filename suffix (`.component.tsx`, `.layout.tsx`, `.error-boundary.tsx`,
`.tsx`), so moving a naming convention can turn a rule into a silent no-op — and
a dead rule reports exactly what compliant code reports: nothing. That is what
happened to `no-type-definitions-in-components`, which went on matching the
camelCase `.errorBoundary.tsx` spelling after `filename-convention` had replaced
it, and so fired on none of the repo's error boundaries.

A filename-gated rule must therefore assert **both sides of its gate**: the same
source is `invalid` under a matching filename and `valid` under a non-matching
one. A test that only checks the violation cannot tell a working rule from a
dead one.

An option needs the same treatment, for the same reason: assert that configuring
it works _and_ that leaving it unset does not change what the rule reports.

## Build and Consumption

`exports` points at `src`, so nothing in this repo builds before it can lint —
ESLint loads the rules through Node's type stripping, resolving the workspace
symlink to a real path outside `node_modules`. `publishConfig.exports` swaps to
`dist` at pack time, because that same `.ts` file inside a consumer's
`node_modules` is not loadable at all
(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`).

This is why the package must be imported **by name**. It was previously loaded
through the relative path `../eslint-local-rules/index.js` from
`packages/vite-configs` — an undeclared cross-package edge (ADR-039) that no
external consumer could reproduce, since nobody outside this repo has a
`../eslint-local-rules/`.

- Built with: `vp pack` (`vp run --filter @lcabrera/eslint-plugin build`)
- Consumed by the shared ESLint flat-config helpers:
  - `packages/vite-configs/src/eslint.custom-rules.shared.config.mjs` (React)
  - `packages/vite-configs/src/eslint.base-custom-rules.shared.config.mjs` (non-React)
- App roots consume those helpers via `@lcabrera/vite-config/eslint-custom-rules`.

`@lcabrera/vite-config` takes a runtime `dependency` on this package, so this
package must **not** depend on it back — that cycle breaks every recursive
`vp run -r` task graph. Its `eslint.config.mjs` therefore imports the shared
config by relative path, and its `vite.config.ts` inlines the pack and coverage
settings. `@lcabrera/utils` used to resolve the same cycle the same way and no
longer needs to: ADR-069 dropped it from the config package's dependencies.

## Guardrails

- Rule IDs remain stable under `local-rules/*` so existing inline disable
  comments keep working. The published package name does not force that prefix:
  the plugin is registered under an explicit key in the flat config, and a
  consumer picks their own.
- React-only behavior is controlled by consuming app file globs, not by
  duplicating plugin implementations.
- The exported surface is snapshotted in `reports/api-surface/eslint-plugin.txt`
  and gated by `vp run api-surface:verify`, so a changed message ID or option
  shape cannot reach the registry silently.
- Anything a consumer would have to match to use a rule — an alias, a filename
  suffix, a naming migration — is an option with a default, not a constant.
